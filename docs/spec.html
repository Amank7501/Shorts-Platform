Shorts Platform: Build Spec

A personal tool that turns a prepared script into a finished faceless YouTube Short. This page is the single source of truth for what we are building and how.

The idea

The manual workflow uses several AI tools one after another to make a faceless Short. We automate everything after the script is ready, and put an in-app editor where the user can review and fix the video before it renders.

You do manually (for now)

  • Research and topic choice
  • Splitting the transcript into scenes (about 5 seconds of speech each), with a visual prompt per scene
  • Uploading the final MP4 to YouTube

The platform does

  • Per-scene voiceover and word timing, an image or clip for each scene, assembly
  • A pause for review and editing in the browser
  • Final 9:16 render and MP4 download
Audience: personal use only, not a product for others. That is why auth, billing, and heavy infrastructure are out of scope.

Pipeline

One LangGraph graph, one node per step. State is saved in a SQLite checkpointer, so the graph can pause at review for as long as needed and resume when the user approves.

VoiceoverTTS, per scene
TimingWhisper, per scene
Mediastock first, then generated
Assemblebuild video JSON
Reviewgraph pauses (interrupt)
Renderper-scene segments, local
Donedownload MP4

Input to the graph is the scenes JSON: one script line per scene, plus a visual prompt for each. Voiceover, timing, and media nodes work per scene, and scenes run in parallel.

What each node does

NodeWork
VoiceoverOne TTS call per scene (ElevenLabs, OpenAI TTS, or Google TTS), saved as one audio file per scene. Its length sets that scene’s duration.
TimingRun Whisper on each scene’s audio for word-level timestamps, used for captions.
MediaFind an image or clip for each scene: stock first, image generation as fallback. See Scene media below.
AssembleWrite everything into the video JSON: scenes, chosen media, per-scene audio, captions, timings.
ReviewInterrupt. The user edits in the browser. Approve resumes the graph.
RenderRender each scene as its own segment, join the segments into one 9:16 MP4 on the local machine. See Render design below.

State held by the graph: project ID, scenes, per-scene audio keys and timestamps, media candidates, video JSON, status.

Scene media

Each scene gets one image or video clip. The system pre-selects the best candidate and the user can swap it. Order of sources: stock first, generation as fallback, and the user can always upload their own.

How media is chosen

  • Stock search: use the scene’s visual prompt on Pexels and Pixabay. Keep only vertical media above a minimum resolution, rank by embedding similarity (CLIP) between the scene text and the media, and keep up to 3 candidates.
  • Generation fallback: used when no stock candidate matches well enough, or when the user switches the scene to generated. Add a project-level style prefix to every prompt so the video looks like one set. Generate vertically and larger than the frame, to leave room for pan and zoom. Make 1 or 2 images up front and more only through Regenerate.
  • Upload: the user can replace any scene’s media with their own file.
  • Across the video: never reuse the same media, and prefer variety between neighboring scenes.
  • Caption-safe area: captions and the Shorts interface cover the bottom and right edges, so keep the subject in the upper-middle area or set the focal point to push it there.

Automatic quality scoring with a vision model is left for later, only if the user keeps making the same picks by hand.

Turning an image into video

Still images get a slow zoom or pan (Ken Burns). It is a transform over time, so no AI is involved and it is cheap to render. In Remotion it is a CSS transform driven by the frame number.

  • Presets: zoom in, zoom out, pan left, pan right, pan up, pan down, chosen in a rotation so neighboring scenes never repeat the same move.
  • Duration comes from the scene’s voiceover, so any image fits any scene length.
  • The user can set a focal point so the zoom aims at the key object.
  • Stock video clips are also allowed. They are trimmed or looped to the scene length.

Render design

  1. Audio is the master clock. A scene’s duration is its voiceover length plus a short pad. It is not fixed at 5 seconds. Media is trimmed or looped to fit the audio, and a still image has no length of its own, so drift is prevented by design.
  2. Normalize at ingest. When a clip is downloaded, transcode it once with FFmpeg to 1080x1920, 30 fps, H.264, no audio, with its length capped. Also make a small low-resolution proxy for smooth scrubbing in the editor.
  3. Render per scene, with a cache. Each scene renders as its own segment (media, motion, captions, and its own audio), keyed by a hash of that scene’s JSON. Editing a scene re-renders only that segment. Segments are then joined with FFmpeg. This means hard cuts only, and captions never span two scenes.
  4. Validate before rendering. Check the video JSON against its schema (files exist, trims in range, durations add up). Support rendering a short range for spot checks, and log FFmpeg stderr.
  5. Draft and final modes. Draft is half scale with a faster encoder preset, for quick checks. Final quality runs after approval.

The editor preview uses the Remotion Player and needs no render, so render time is paid once per export, plus changed scenes.

Open decision: Remotion or FFmpeg alone for rendering segments. We start with Remotion because preview and output come from the same component. Time a test render with dummy clips (build step 2) and switch to FFmpeg if it is too slow.

What the user sees

  1. Input: paste the scenes (one script line each, with a visual prompt), then click Generate.
  2. Progress: a live step tracker (voiceover done, timing done, footage 5/12, and so on). A failed step shows a retry button.
  3. Editor: the graph is paused here. The user previews the video and fixes what is wrong, then clicks Approve.
  4. Export: render progress, then a download button for the MP4.

Editor capabilities (kept minimal)

Layout: the preview player on top, a thumbnail strip of all scenes below with a status mark on each (ok, needs attention, failed), and a side panel for the selected scene. An Approve All button covers the case where the defaults look fine.

  • Script line and its voiceover: edit and regenerate. Only that scene’s audio, timing, and segment are redone, so later scenes are not affected
  • Media candidates: click to swap, Regenerate with an editable prompt, or upload
  • Source switch: stock, generated, or uploaded
  • Motion preset and a focal-point picker
  • Caption text and style
  • Trim the media or change its start point
  • Reorder scenes

A full timeline editor is a separate project and is not planned. Extra features are added only when the same fix keeps being done by hand.

The video JSON

This is the contract for the whole system. Pipeline nodes write it, the editor edits it, and Remotion reads it for both preview and final render. The same component renders both, so the preview matches the output. It must be defined before anything else.

It holds, for each scene: the script line, its own audio file and duration, the chosen media and its source (stock, generated, or uploaded), the motion preset and focal point, and captions with word timings and style. It also holds the 9:16 output settings. Files are referenced by storage key, never by absolute path.

Storage

All files live on the local disk. Keep a clean path to S3 later by following these rules from day one:

  • One small storage interface: save(file) → key, get(key) → path or URL, delete(key). No other code touches file paths.
  • Store keys (for example projects/42/clips/scene_03.mp4) in the video JSON, not absolute paths.
  • Folder layout: storage/projects/{id}/{audio|clips|renders}/.
  • The backend serves files over HTTP (GET /files/{key}), because the Remotion Player needs URLs.
  • Delete unchosen candidate clips once a project is approved.

Backend API

Paths sit under /api. Long jobs return immediately and run in the background. The frontend polls status every 2 to 3 seconds while a job runs.

Frontend

  • Pages: Projects list, New project (input), Progress, Editor, Export.
  • Editor layout: player on top or left, a scene strip below, and a side panel for the selected scene (clip candidates, caption text, voice line).
  • State: the video JSON lives in a Zustand store. Edits update the store and the preview instantly. Changes save to the backend with debounced autosave.
  • Progress: polling, with no SSE or WebSocket.

What runs locally

  • Whisper: light for this use. A 30-second clip with the small model takes roughly 5 to 15 seconds on a normal laptop CPU and about 2 GB RAM. It transcribes clean TTS audio accurately. A GPU is not required.
  • Render: the heaviest local step. It uses CPU for around a minute or two per video.
  • Backend, frontend, storage: light.
  • Everything else (TTS, footage search or generation) is an API call and uses no local resources.

Estimate: about $0.10 to $1 per video with stock media and TTS. Each generated image adds to that. To stay cheap: stock first, generate only when needed, Whisper and render local.

Build order

  1. Video JSON schema, storage interface, and database (including music and caption style fields).
  2. Remotion composition and per-scene render with FFmpeg join, tested with dummy clips and timed to settle the Remotion versus FFmpeg decision. Render is the hardest part, so it is proven first.
  3. Per-scene voiceover and word-timed captions.
  4. Media: stock search with CLIP ranking, plus generation fallback.
  5. Thin end-to-end script (scenes JSON in, MP4 out) with a dry-run mode, before any graph or UI.
  6. LangGraph pipeline and backend API, with the review interrupt.
  7. Frontend shell: projects, input, progress, preview, export.
  8. Editor: core fixes first, then the extras (focal point, motion, trim, reorder).
  9. Hardening, then the first real Short.
  10. Later: automate the research and transcript-split steps.

Risks to plan for

  • Render is the hardest step. Drift is prevented by using audio as the master clock, but inputs differ in resolution, frame rate, and codec, so every clip must be normalized at ingest. FFmpeg errors are cryptic and only show after a slow render, so validate the JSON first.
  • Stock matching is unreliable for specific topics. Generic results often miss exact facts. Mitigation: similarity ranking with up to 3 candidates, a generation fallback, and a quick human pick in the editor.
  • Generated-image cost grows with every fallback or regenerate, so generate only when stock fails or the user asks.

Out of scope for now

  • Auth, user accounts, billing, and quotas
  • Postgres, Redis, and S3 (SQLite and local disk instead)
  • SSE and WebSocket (polling instead)
  • Docker and deployment
  • YouTube API upload (upload is manual)
  • Automated research and transcript splitting (manual for now)
If this ever becomes a product: add auth, Postgres, a proper job queue, and S3. A clean video JSON and the storage interface make that upgrade much easier.

Build phases (0 to 100)

The build is done with Claude Code, one phase at a time. Phases are vertical slices: each ends with something you can run. The percentage is overall progress once that phase is done. Phase 0 is preparation, so it stays at 0%. Manual steps are the things only you can do (accounts, keys, installs, listening and choosing).

Working with Claude Code

  • Put this spec in the repo (for example docs/spec.html) and add a short CLAUDE.md that points to it and lists the run commands. Every session then starts from the same source of truth.
  • One phase per session. Ask Claude Code to plan first, then build, then run the phase’s “done when” check.
  • Commit at the end of every phase so you can roll back.
  • If a decision changes, update this spec first, then continue building.

Phase 0 (0%): Setup and scaffold

Manual setup
  • Install recent versions of Node.js, Python, and FFmpeg (check that ffmpeg and ffprobe run in a terminal).
  • Create accounts and API keys for: a TTS provider (ElevenLabs, OpenAI TTS, or Google TTS), Pexels, Pixabay, and one image generation API.
  • Create the git repo, add the spec, and write the keys into a local .env file (never commit it).

Claude Code: create the project layout (backend/, frontend/, storage/), config loading from .env, SQLite setup, and CLAUDE.md.

Done when: backend and frontend both start with one command each and an empty page loads.

Phase 1 (8%): Contract — video JSON, storage, database

Claude Code: define the video JSON schema with a validator, the storage interface (save, get, delete) over the local folder, the SQLite tables for projects, and a few sample JSON fixtures with tests. Include the fields that are costly to add later: background music with ducking, and a caption style.

Manual: review the schema and confirm it holds everything the spec lists for a scene (script line, audio and duration, media and source, motion and focal point, captions), plus music and caption style.

Done when: sample JSON validates, bad JSON is rejected with a clear message, and files save and load by key.

Phase 2 (22%): Render proof

Claude Code: build the Remotion scene composition (media, slow zoom or pan, captions, audio), per-scene segment render with the hash cache, FFmpeg normalize-at-ingest, and the FFmpeg join into one 9:16 MP4. Add draft and final modes. Use dummy assets only.

Manual: drop in a few sample images, a short clip, and sample audio files. Time a full render on your machine and write the time down.

Done when: a dummy 10-scene video renders end to end, and editing one scene re-renders only that scene. Use the measured time to settle Remotion versus FFmpeg-only.

Phase 3 (32%): Voice and captions

Claude Code: per-scene TTS, word timestamps from faster-whisper (or alignment against the known script text), and caption styling in the composition.

Manual: let Whisper download its model on first run, listen to a few voiceover samples and pick the voice, and choose the caption style.

Done when: a real scenes JSON produces per-scene audio and word timings, and a render shows correctly timed captions.

Phase 4 (45%): Media

Claude Code: Pexels and Pixabay search with vertical and resolution filtering, CLIP similarity ranking with up to 3 candidates, the image generation fallback with the style prefix, the upload path, and the no-reuse rule across the video.

Manual: write the style prefix for generated images, and judge the candidates by eye to tune the “good enough” threshold that triggers generation.

Done when: a real scenes JSON gives candidates for every scene, saved in storage.

Phase 5 (55%): Thin end-to-end slice

Claude Code: a plain script or CLI that chains phases 3, 4 and 2 with no graph and no UI. Add a dry-run mode with stub providers (fake TTS and images) so later phases can be built without spending API credits.

Manual: run a real scenes JSON through it and look at the video.

Done when: scenes JSON in, finished MP4 out. This is the first usable output.

Phase 6 (68%): Backend API and LangGraph pipeline

Claude Code: the core-loop endpoints, the LangGraph graph with the SQLite checkpointer, per-scene parallel nodes, the review interrupt, approve that resumes the graph, file serving, and status polling. Do a small spike first on interrupt combined with parallel fan-out and the SQLite checkpointer.

Manual: run it with a real scenes JSON using only API calls (no UI yet) and check each step’s output.

Done when: run, pause at review, approve, and render all work through the API, and the graph survives a backend restart while paused.

Phase 7 (78%): Frontend shell

Claude Code: projects list, input screen, progress screen with polling, export screen with download, and the Remotion Player previewing the video JSON.

Done when: you can paste scenes, watch progress, preview the result, and download the MP4 from the browser, with no editing yet.

Phase 8 (87%): Editor core

Claude Code: the scene strip with status marks, the side panel for swapping media candidates and regenerating them, editing the script line with voice regenerate, caption text, debounced autosave, the matching editor-action endpoints, and Approve All.

Manual: use the editor on a real project and note which fixes you reach for most. Those drive priorities.

Done when: you can fix the common problems without touching the JSON, and a single-scene edit re-renders only that scene.

Phase 9 (92%): Editor extras

Claude Code: source switch (stock, generated, uploaded), focal-point picker, motion preset, media trim, scene reorder, and low-resolution proxies for smooth scrubbing.

Done when: every edit in the spec works and previews instantly.

Phase 10 (97%): Hardening

Claude Code: the per-step retry endpoint, clear error messages, JSON validation before render, cleanup of unchosen candidates after approval, handling of a backend crash mid-run, and a short README with run steps.

Manual: run 3 to 5 real videos end to end and log anything that breaks or feels slow.

Done when: those runs finish without manual fixes in the code.

Phase 11 (100%): First real Short

Manual: make one real Short from research to export, then upload it to YouTube yourself.

Done when: the video is live, and you have a short list of what to improve next, such as automating research or the transcript split.
